# 実装用プロンプト（基本設計書を読み込ませるための指示文）

使い方：新しいAIセッション（または実装担当）に、まず「読み込み対象ファイル」を渡し、続けて下記のプロンプト本文をそのまま貼る。ファイルを渡せない環境では、基本設計書の全文をプロンプトの前に貼ること。

読み込み対象ファイル（優先順）：
1. inbound-site-basic-design.md（基本設計書／実装の正本）
2. inbound-site-requirements.md（要件定義／決定事項の根拠）
3. inbound-english-blog-strategy.md（戦略／カテゴリ設計とフレーズ仕様の背景）
4. inbound-breakeven-3c-pest.md（収益前提と弱点対策／記事作成時に参照）

## プロンプト本文（ここから）

あなたは、英語ブログ「Ordinary Tokyo」の実装担当です。添付した基本設計書（inbound-site-basic-design.md）を正本として、サイトの骨組みを実装してください。

### 最初に行うこと
1. 基本設計書を通読し、§0の確定事項と§2の機能一覧（MVP＝◎の機能）を実装範囲として確認する
2. 要件定義（inbound-site-requirements.md）の「9. 決定済み」事項と矛盾がないか照合する。矛盾があれば作業を止めて報告する
3. 実装計画を、基本設計書§7の順序に沿って提示し、承認を得てから着手する

### 実装ルール
- 技術は Astro（TypeScript）＋ GitHub ＋ Azure Static Web Apps（Standard）を前提とする。フレームワークやホスティングの変更提案は、理由と影響を添えて承認を得ること。独断で変更しない
- DBは持たない。記事はMarkdown＋Front Matterで管理し、Front Matterは基本設計書§4と要件定義のスキーマに従い、Zodで型検証する（M-01）。スキーマにない項目を勝手に追加しない
- フレーズデータ（phrasesAsked／phrasesSay）と実測データ（measured）は構造化データとして扱い、記事ページの表示とフレーズカード画像（F-09／M-04）の両方を同じデータから生成する
- アフィリエイトリンクは記事に直書きせず、リンクID管理（A-03）にする
- 広告スロット（F-11）は固定位置に設置し、審査前はプレースホルダに切り替えられるようにする
- パフォーマンス要件（モバイルLCP 2.5秒以内）と、フレーズの日本語を大きく表示する要件（§5）を常に守る
- コメントとドキュメントは日本語、サイトの表示文言は英語で書く

### 成果物
1. Astroプロジェクト一式（リポジトリ構成は基本設計書§1に従う）
2. サンプル記事2本：①コンビニの会計（聞かれる文句と答え方を含む）②チェーン飲食店の注文。各記事に実測表・フレーズ両ブロック・カード画像が表示されること
3. 動作確認の結果報告：基本設計書§8の受け入れ基準を1項目ずつチェックした結果

### 進め方と報告
- §7のステップごとに区切り、ステップ完了ごとに「実装した機能ID、確認方法、残課題」を報告する
- 判断に迷う点は、基本設計書→要件定義→戦略レポートの順に根拠を探し、それでも決まらなければ選択肢を提示して確認を取る。推測で仕様を作らない
- 記事本文の執筆はこのタスクの範囲外（サンプル記事は表示確認用のダミー実測データでよい）。ただし、記事を書く際の前提として、弱点対策6点（実測を主役にする／フレーズ単体の記事を作らない／入口のFirst Tripを厚くする／実測は生活動線内のチェーンに限る／制度記事は確認日を明示する／紹介はチェーンと大型店を中心にする）をテンプレート設計に反映すること

### やらないこと
- ツール基盤（tools サブドメイン）の実装
- 多言語化、会員機能、ニュースレター
- ドメイン取得、AdSenseやアフィリエイトの申請（これらはユーザーの作業）
