# インバウンド英語ブログ 開設〜審査 実行プラン（詳細版）

作成日：2026-11-26
進め方（ユーザー指示）：サイト開設からASP／広告の審査まではハイペースで進める。ひな型が完成した後の投稿ペースは週2〜3本。
前提：書き手は東京在住・勤務中。対象は東京の日常＋全国チェーン。記事は英語、フレーズ標準装備つき（戦略レポート参照）。

凡例：担当はユーザー／Claude／共同判断。各項目に「決めること」を明記する。

---

## 全体スケジュール（ハイペース版の目安）

- Week 1：プラットフォーム選定、要件定義、ドメイン取得、サーバー契約
- Week 2：設計（情報設計・デザイン・テンプレ仕様）
- Week 3〜4：実装（MVP）、必須ページ、計測設定
- Week 4〜5：初期記事10本の制作（実測含む）と公開、ひな型の完成
- Week 5〜6：AdSense申請、Amazonアソシエイト申請、旅行系アフィリエイト申請（審査待ちの間に記事を増やす）
- 審査通過後：週2〜3本の定常運用へ移行

※審査期間はコントロールできないため、「申請までをハイペース」にし、審査待ち期間を記事蓄積に使う設計とする。

## 1. 公開用サイトのプラットフォーム選定

### 候補と比較軸
| 候補 | 概要 | 向いている点 | 注意点 |
|---|---|---|---|
| A. 自作（Django＋TypeScript） | ユーザーの技術選好どおり自前実装 | 完全な自由度、ツール（後述の便利ツール群）を同居できる、保守を自分で制御できる | 初期実装コスト、セキュリティ保守は自己責任 |
| B. 静的サイト生成（Astro／Next.js等＋ホスティング） | 記事は静的生成、ツールはクライアント側JS | 表示が高速（SEOとAdSense単価に効く）、サーバー保守がほぼ不要、ホスティング費が安い | 動的機能が必要になると構成が複雑化 |
| C. 既存プラットフォーム（WordPress等） | レンタルサーバー＋CMS | 立ち上げ最速、プラグインでSEO／広告が揃う | PHPを避けたいというユーザー選好と衝突。カスタムツールの同居が弱い |
| D. note等の既存メディア | 既存アカウント活用 | 開設ゼロ分 | 英語読者に届かない、AdSense不可、カスタム広告不可。本企画では不採用（戦略レポートで確定済み） |

### 決定（2026-11-26）：B案（静的サイト）を採用
- 本体は静的サイト生成＋ファイル運用（Markdown＋Front Matter、pushで自動ビルド・公開）とする。費用面の強さと、記事生産の主担当がClaudeであることが決め手
- ツールを作成することになった場合は、本体には同居させない。**サブドメインを切り、別途 Azure Web Apps 等を用意してリンクする形式**とする（例：tools.ドメイン名）。これにより本体の静的構成と表示速度を維持したまま、ツール側だけ動的な実装を選べる
- 管理画面が欲しくなった場合は、GitベースCMSの後付けで対応する（DBは持たない）

### 選定で決めること（決定前の論点メモ）
- 本命はAかB。判断軸は「バックエンドが要るか」（次項）と「ツール同居を本気でやるか」
- パターン1（無料webアプリ公開）と基盤を共用するか、別サイトにするか。共用するとドメイン評価と保守が1つで済むが、テーマが混ざるとAdSense審査とSEOの専門性が下がる。**推奨は別ドメイン・同一基盤（同じサーバー／同じコード資産）**
- 既存プラットフォームは「開設速度最優先で検証だけしたい」場合の保険として残す

## 2. 自作の場合の要件定義（クが叩き台を作成）

### 2-1. MVP（最初に公開する最小構成）
- 記事の表示・一覧・カテゴリページ（ステージ×領域の2軸タグ）
- 記事テンプレート：Quick Answer、実測データ表、You'll be asked／Say this・Show this（フレーズブロック）、見せる用カード画像、Disclosure表記、確認日表示
- 必須ページ：About（Tokyo localであることの明記）、Privacy Policy、Contact、Affiliate Disclosure
- 基本SEO一式：sitemap.xml、robots.txt、OGP、構造化データ（Article／FAQ）、パンくず
- 計測：Google Analytics 4、Google Search Console の設置
- ads.txt の設置場所（AdSense用）
- スマホ前提のレスポンシブと表示速度（Core Web Vitals：LCP 2.5秒以内を目標）

### 2-2. 追加項目（MVPの後）
- フレーズカードの自動生成（記事データからカード画像を量産する仕組み）
- 記事内検索、関連記事の自動提示
- 多言語化はしない（英語一本）。ただし将来の拡張余地としてURL設計だけは言語プレフィックス対応にしておく
- ニュースレター／SNS連携（Pinterest自動投稿など）
- 広告ネットワークの追加枠（Ezoic等はPV条件を満たしてから）

### 2-3. 用途の高いツール（サイト内蔵の便利ツール）
パターン1（webアプリ公開）の資産を、インバウンド向けに転用して同居させる案。記事の回遊と滞在時間を稼ぎ、検索流入の別入口になる。
- 為替換算（円⇔ドル等の目安表示。レート取得元と更新頻度を要精査）
- 免税計算（5,000円以上の買い物でいくら戻るか、消耗品の合算ルールつき）
- チップ不要の明示を含む会計シミュレータ（割り勘計算）
- サイズ換算（靴・服の日本サイズ⇔US／UK／EU）
- 日付・時刻換算、気温換算（℃⇔℉）等の小物
- 優先順位はフェーズ0の検索クエリ調査で決める。全てフロントエンド完結が基本

### 2-4. バックエンドの必要可否
- 記事配信だけならバックエンドは不要（静的生成で足りる）。Django／FastAPIが必要になるのは次の場合のみ：
- 為替レート等の外部APIを定期取得してキャッシュする場合（軽いバッチで代替可能）
- お問い合わせフォームの受け口（外部フォームサービスで代替可能）
- 将来の会員機能・有料機能（現時点では計画なし）
- 精査結論の出し方：「静的＋小さなAPI1本」で足りるかを機能一覧から逆算し、過剰な構成にしない。ユーザーの選好（Django＋TypeScript）と両立させるなら、Djangoは管理・バッチ側、公開側は静的生成という分離も候補

### 2-5. サーバーのリージョン
- 読者は米国・欧州・豪州・東南アジアに分散し、日本国内読者はほぼいない前提
- 選択肢：①米国リージョンのホスティング ②CDN（Cloudflare等）を前段に置けば配信元リージョンの影響は小さい
- 推奨の考え方：**配信はCDN前提で全世界対応にし、サーバー本体は保守しやすい場所に置く**。リージョン選定よりCDNとキャッシュ設計が体感速度を決める
- 費用感：小規模ホスティング＋CDN無料枠で月数百〜数千円に収める

### 2-6. ドメイン
- 条件：英語圏読者が覚えやすい、日常（everyday／local）の含意がある、.com が取れる、商標衝突がない、SNSの同名アカウントが取れる
- Claudeが候補を10〜20件出し、空き状況を確認してからユーザーが最終決定・取得する
- サイト名とドメインは同時に決める（後の変更はSEO資産のロスになるため、ここは急がず1回で決める）

## 3. 公開用サイトの設計

- 情報設計：カテゴリ（ステージ3×領域4）、タグ（チェーン名、場面名）、記事同士の内部リンク規則（初回記事→リピート記事への導線）
- デザイン：モバイルファースト、フレーズカードが映えるレイアウト、実測表の共通スタイル、広告スロットの固定位置（記事冒頭下／中盤／末尾）
- テンプレート仕様書：記事の固定セクションと文字量の目安、写真の点数と撮り方の基準（パッケージ表裏、中身、価格タグ、店内の様子は許可範囲で）
- ブランド要素：ロゴ、アイコン、色、フォント（英語圏向けの可読性優先）
- 運用設計：記事データの管理形式（実測メモ→記事化のフロー）、更新日の管理、季節品の差し替え手順

## 4. 公開用サイトの実装

- 実装の分担：コードの作成と動作確認はClaude側で進められる範囲を最大化する。ユーザーはサーバー契約・ドメイン取得・本番公開の承認と、実機（スマホ）での見え方確認を担当
- 環境：開発→検証→本番の3段階。本番反映はユーザーの承認後
- 公開前チェックリスト：表示速度、スマホ表示、リンク切れ、構造化データの検証、Search Consoleへのサイトマップ送信、404ページ、HTTPS
- バックアップと監視：コンテンツの自動バックアップ、障害に気づける最低限の監視

## 5. 契約が必要なもの（Google AdSense、Amazonアソシエイト以外）

### 必須級
- **Google AdSense**：表示広告の土台。審査あり（記事数と必須ページが前提）
- **Amazonアソシエイト（USを主、必要に応じUK等）**：帰国後も買える日本商品の出口。審査あり（一定期間内の売上条件に注意）。日本のAmazonアソシエイトとは別契約になる点に注意
- **Travelpayouts**：航空券・ホテル・ツアー・eSIM等の横断ネットワーク。KlookやBooking.com系ブランドをまとめて扱える入口になる

### 推奨（記事の型が決まったら追加）
- **Klook**（Travelpayouts経由または直）：アクティビティ・交通パス・eSIM。報酬2〜5%
- **Booking.com**（同上または直）：宿泊。報酬3〜5%
- **Awin／Impact**：日本製品の越境ECや個別ブランド案件の受け皿
- **もしもアフィリエイト／楽天アフィリエイト**：日本側の商品リンクが必要な場合の補助（英語読者向けの主軸にはしない）

### 受け取り・税務まわり（見落としがちな必須確認）
- 海外プログラムの報酬はドル建て・PayPalや海外送金が中心。**受け取り口座（PayPal、Wise等）の準備**が登録と並行で必要
- 最低支払額と支払いサイクルはプログラムごとに確認（未達だと報酬が滞留する）
- 副業収入としての確定申告の扱いは、収益が発生する前に一度確認する（金額が小さいうちは論点も小さい）

### 不要・後回し
- 国内ASP（A8.net等）はAI検証側の文脈では優先だったが、本企画の読者は海外のため優先度は下がる。日本企業の海外向け案件が出てきた場合のみ追加

## 6. SEOなどの宣伝戦略

### SEO（本命）
- キーワード設計：購買・行動意図のあるロングテール（例：what to buy at japanese convenience store、saizeriya menu english、how to use suica 等）をフェーズ0で100件規模で収集し、ステージ×領域のマスに割り当てる
- 記事の型：Quick Answer先行、実測表、フレーズ装備、FAQ＋構造化データ、確認日の明示と月次更新
- 内部リンク：初回記事をハブにし、リピート記事へ送る回遊設計。チェーン別・場面別のまとめページ（ピラーページ）を作る
- 被リンク施策：Redditの日本旅行コミュニティや旅行フォーラムでの有用な回答（宣伝ではなく回答として）、旅行系メディアへの寄稿は後段
- 技術面：Core Web Vitals、モバイル最適化、画像の軽量化とalt、英語のURLスラッグ

### SNS・その他（補助）
- **Pinterest**：旅行計画層が強く、英語圏との相性が良い。フレーズカードと商品写真がそのまま素材になる
- **YouTube Shorts／TikTok**：購入品の開封と発音の短尺。制作コストが高いので、記事が回り始めてから検討（ユーザーの時間制約を考慮し初期は対象外）
- SNSアカウント名はドメインと統一し、開設時に同時取得する

### やらないこと
- 有料広告（審査前のPV購入は費用対効果が合わない）
- 相互リンク等のブラックハットSEO（AdSense審査と長期評価を毀損する）

## 7. 掲載商品の選定

### 選定基準（編集原則と一致）
1. 日本人が実際に使い、満足してリピートしているもの（最優先）
2. 価格が手頃で実測コストが小さい（100〜2,000円中心）
3. 海外でも買える導線があるもの（Amazon等）は収益面で優遇、無いものはPVで回収と割り切る
4. 季節限定・新商品は鮮度枠として別管理

### 初期リストの作り方
- 領域ごとに候補を出す：コンビニ定番（おにぎり、FamiChiki、からあげクン、Uchi Café等）、100均のアイディア商品、ドラッグストアの定番、業務スーパー・OKストアの生活品、チェーン飲食の定番メニュー
- 各候補に「実測コスト、買える場所（ユーザーの生活動線内か）、広告の出口の有無」を付けて優先順位を付ける
- 初回ロットは「ユーザーが普段から買っているもの」から選ぶ。実測の追加コストと時間がほぼゼロになる

## 8. 記事のジャンル分け

- 一次分類は戦略レポートの2軸（ステージ3段階×領域4つ）をそのままサイトのカテゴリに使う
- 二次分類（タグ）：チェーン名（7-Eleven／FamilyMart／Lawson／Saizeriya等）、場面（会計／注文／買い物／移動）、目的（食べる／買う／使う）
- まとめページ：チェーン別ハブ、ステージ別ハブ（First Trip Guide等）をピラーページとして用意し、個別記事をぶら下げる
- ジャンルごとの記事テンプレ差分：飲食店記事は注文フロー中心、買い物記事は商品比較表中心、インフラ記事は手順中心に、フレーズの置き場を変える

## 追加で洗い出した「やらなければいけないこと」（ユーザーのリストへの補足）

- **法務・表記ページ**：Privacy Policy、Affiliate Disclosure（FTC基準）、Cookie同意（EU読者向けのGDPR対応バナー要否）、免責（価格は確認日時点の表示）
- **AdSense審査の前提整備**：記事10〜15本、必須ページ、独自写真。審査は「サイトの完成度」を見るため、ひな型完成と初期記事が揃うまで申請しない
- **Amazonの審査条件管理**：申請後の売上発生期限があるため、記事と導線が揃ったタイミングで申請する（早すぎる申請は失効リスク）
- **計測と判定の仕組み**：GA4とSearch Consoleの初期設定、月次のKPI集計フォーマット、6か月判定の撤退ライン数値（フェーズ0で確定）
- **画像の権利と撮影ルール**：店内撮影の可否は店ごとに確認し、不可の場合は購入品の自宅撮影で統一する。他人の顔・レシートの個人情報が写り込まない基準も決める
- **アカウント一式の同時取得**：ドメイン、SNS（Pinterest、X、Instagram等）、Googleアカウント系を名前統一で押さえる
- **コスト管理表**：ドメイン・サーバー・商品購入費の月次上限を決め、実測費の記録方法を統一する
- **リスク対応**：AdSense審査に落ちた場合の再申請手順、為替変動でRPMが動く前提の収益試算（保守／標準／楽観の3ケース）
