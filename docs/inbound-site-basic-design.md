# Ordinary Tokyo 基本設計書

作成日：2026-11-26／版：1.0
位置づけ：本書は実装の正本である。要件定義（inbound-site-requirements.md）で決めた内容を、機能単位に落としたもの。戦略の背景は inbound-english-blog-strategy.md、収益前提は inbound-breakeven-3c-pest.md を参照するが、**実装判断で迷ったら本書を優先する**。

## 0. 確定事項（前提として動かさない）

- サイト名：Ordinary Tokyo／ドメイン：ordinarytokyo.com
- 方式：静的サイト（B案）。記事はMarkdown＋Front Matterのファイル運用
- 技術：Astro（TypeScript）＋ GitHub ＋ Azure Static Web Apps（Standard）
- ツール基盤：初期は作らない。将来は tools.ordinarytokyo.com に Azure Web Apps（Linux）で分離し、リンクで接続する
- 言語：英語のみ（多言語化しない。URLは将来に備え言語プレフィックスなしの素の構造にする）
- 書き手表記：顔出し・本名なし。「Tokyo-based Japanese local」の属性のみ
- 更新運用：ひな型完成後は週2〜3本。記事作成時は弱点対策6点（実測主役／フレーズは文脈に埋める／入口を厚く／生活動線で実測／制度記事は確認日明示／紹介はチェーン中心）を必ず守る

## 1. システム構成

```
[GitHub リポジトリ]
  ├─ src/content/articles/*.md   記事（本文＋Front Matter）
  ├─ src/assets/…                画像（記事ごとにサブフォルダ）
  └─ public/                     ads.txt, favicon 等
        │ push (main) / PR
        ▼
[GitHub Actions] Astro build（スキーマ検証→静的生成→カード画像生成）
        ▼
[Azure Static Web Apps Standard] 本番配信（CDN＋HTTPS、独自ドメイン）
        ├─ ordinarytokyo.com        本体
        └─ （将来）tools.ordinarytokyo.com → Azure Web Apps（別リポジトリ可）
[計測] GA4 / Google Search Console（タグは全ページ共通レイアウトに設置）
```

- プレビュー：PRごとにプレビュー環境を自動生成し、ユーザーがスマホで確認してからマージする
- ロールバック：前コミットへ戻すことで即時復旧できる構成にする

## 3-2. ページデザイン設計（レイアウト・配色・タイポグラフィ）

設計の原則：**英語圏の読者が「いつもの旅行ブログ」として迷わず読めること**を最優先にする。日本的な装飾で奇をてらわず、欧米の旅行メディアで標準的な型に、日本の日常という中身と実測・フレーズの機能を載せる。

### レイアウト（英語圏の標準型）
- 全ページ左揃え、十分な余白（ホワイトスペース）を取る。中央揃えの多用と、文字の詰め込みは避ける
- 記事ページの標準構成（上から）：パンくず → タイトル → メタ行（著者・公開日・更新日・読了目安） → ヒーロー画像 → **Quick Answer（結論ボックス）** → 目次（アンカーリンク、スクロールに追従する sticky 表示） → 本文（H2ごとに1トピック） → FAQ（アコーディオン） → 著者ボックス → 関連記事カード
- この「タイトル→結論→目次→本文→FAQ→著者」の流れは、欧米の旅行ブログ（Nomadic Matt型）や情報サイトで読者が慣れ親しんだ型であり、AI検索時代の構造化（結論先行、FAQ）とも一致する
- 一覧ページはカード型グリッド（画像・タイトル・要約・メタ）が標準。1カラムのリスト形式は使わない
- ヘッダーは sticky（ロゴ左、ナビ中央〜右、検索アイコン右）。フッターは3〜4カラム（About、カテゴリ、必須ページ、SNS）
- 本文カラム幅は読みやすい 680〜760px を上限とし、広い画面ではサイドバー（目次・人気記事・広告）に使う2カラム

### 配色（カラーパレット）
日本の色から採るが、彩度を落として欧米の読者に馴染む清潔感を優先する。

| 役割 | 色 | HEX | 用途 |
|---|---|---|---|
| ベース背景 | オフホワイト | #FAFAF7 | ページ全体の背景 |
| 本文テキスト | 墨色（チャコール） | #22252A | 本文・見出し |
| プライマリ | 藍色（インディゴ） | #1F3A5F | ヘッダー、見出しアクセント、リンク、ボタン |
| アクセント | 朱色（バーミリオン） | #D64533 | CTA、強調、バッジ。使いすぎない（1画面に数か所まで） |
| 補助背景 | 薄い藍グレー | #EDF1F5 | ボックス、表の見出し行、カード背景 |
| 罫線 | ライトグレー | #D9DDE2 | 区切り、カード枠 |
| 成功・肯定 | 深緑 | #2E7D52 | 「おすすめ」の表示等 |

- コントラストはWCAG AA（本文4.5:1以上）を全ての組み合わせで満たす。朱色は白背景で大きな文字・太字に限り、本文リンクには使わない（藍色を使う）
- ダークモードは初期は実装しない（旅行中の屋外・店内での読みやすさを優先し、ライト基調で統一）

### フレーズまわりの専用デザイン（差別化の見た目）
- **You'll hear（聞かれる文句）**：補助背景色のパネルに「店員の吹き出し」風の配置。日本語（大きめ）＋ローマ字＋英語訳＋答えの選択肢をボタン風チップで並べ、指でタップして選ぶ感覚を視覚化する
- **Say this（伝える文句）**：白背景に藍色の太枠のパネル。日本語を最大サイズで表示し、「画面を見せる」用途だと一目で分かるデザインにする
- **見せる用カード画像（F-09）**：生成画像は「白に近い背景＋濃い文字＋十分な余白」で統一し、店内の明るい照明でも画面が読みやすいコントラストにする。ロゴとサイト名を小さく入れ、保存・共有されても出典が分かるようにする
- 実測表：見出し行に補助背景、価格は円を主・ドル換算を副として2段表記。数値は右揃え

### タイポグラフィ
- 英語フォント：見出し・本文ともサンセリフ（Inter または Public Sans 系）。欧米の情報サイトで最も標準的な選択で、信頼感と可読性を両立する
- 日本語フォント：Noto Sans JP。フレーズ表示はウェイトを太め（500〜700）にし、本文より明確に大きくする（通常のフレーズで24px以上、見せる用で32px以上を目安）
- 本文サイズ：16〜18px、行間1.7前後。段落は短く（2〜4文）区切り、欧米の読み物リズムに合わせる
- 見出し：H2は太字で十分な上余白、H3は一回り小さく。装飾の下線や色付けは最小限にする

### 画像・ビジュアルの基準
- ヒーロー画像は16:9、実測写真は実物（購入品・パッケージ・価格タグ）を基本とし、AI生成画像やフリー素材で「行ったふり」をしない
- 写真は明るく自然光寄りの色味で統一し、強いフィルターはかけない（実物の色が正確に伝わることを優先）
- アイコンは線画の汎用セット（Lucide等）で統一し、絵文字をUIに使わない

### ロゴ・ブランド
- ワードマーク型（「Ordinary Tokyo」の文字ロゴ）を基本とし、藍色ベースに朱色のアクセントを1点だけ使う案を初期候補とする
- ファビコンは「O」の字か、朱色の円（日の丸を連想させるが直接的すぎない抽象形）を検討し、実装時に最終決定する

### モバイル（最重要の閲覧環境）
- 読者は旅行中のスマホ閲覧が中心。タップ領域は44px以上、フレーズパネルは横スクロールなしで収める
- 記事下部には「この場面のフレーズカードを保存」の導線を固定表示し、店内で開き直せるようにする
- 表示速度の要件（LCP 2.5秒以内）はデザイン側でも守る：Webフォントは必要ウェイトのみ、装飾画像は最小限

## 4. データ設計

- 正本はリポジトリ内のMarkdownファイル群。DBは持たない
- 記事スキーマは要件定義書のFront Matter案を正とし、追加項目は本書で管理する：
  - affiliateLinks: リンクIDの配列（A-03で使用）
  - faq: 質問と回答の配列（FAQPage構造化データと本文末尾の両方に使う）
  - heroAlt: ヒーロー画像のalt（必須にする）
- 命名規則：slugは英語小文字とハイフン、画像は記事フォルダ内に連番＋内容名
- バージョン管理：記事の変更は全てGit履歴に残す。価格改定等の更新は updatedAt と checkedAt を更新する

## 5. 非機能設計

- 性能：モバイルLCP 2.5秒以内。画像最適化（M-05）とJS最小化（Astroのデフォルトを活かす）で担保する
- 表示：モバイルファースト。フレーズの日本語は「見せる」用途のため本文より大きいサイズ（最小でも20px相当）を確保する
- アクセシビリティ：コントラスト比の確保、画像alt必須、見出し階層の正しさ
- セキュリティ：静的配信のため攻撃面は小さい。フォームは外部サービスに寄せ、個人情報を自前で保持しない
- 可用性：Azure Static Web Apps Standard のSLAに依存。デプロイ失敗時は旧版が配信され続ける
- コスト：本体は月約1,600円（損益レポートのフェーズA）に収める。帯域100GB／月を超える見込みになったら、その時点でCDN構成を見直す

## 7. 実装の順序（骨組みの範囲）

1. リポジトリと Astro プロジェクトの初期化、共通レイアウト（S-01の骨格、ヘッダー／フッター）
2. 記事スキーマ（M-01）と記事ページ（S-02、F-03〜F-05、F-10）の実装、サンプル記事2本（コンビニ会計、チェーン飲食の注文）で全ブロックの表示確認
3. 一覧とハブ（F-06、F-07、S-03〜S-05）、関連記事（F-08）
4. カード画像生成（M-04／F-09）、画像最適化（M-05）
5. SEO一式（M-06、M-07）、必須ページ（F-12）、404
6. 計測（A-01、A-02）、広告枠と ads.txt（F-11、A-04）、リンク管理（A-03）
7. Azure Static Web Apps への接続、プレビュー運用（M-03）の確立、独自ドメインの接続手順の文書化（ドメイン取得後に実施）

## 8. 受け入れ基準（骨組み完成の定義）

- サンプル記事2本が、実測表・フレーズ両ブロック・カード画像つきで正しく表示される
- スキーマ違反の記事を入れるとビルドが止まる
- スマホ実機で、フレーズの日本語が「店員に見せて読める」大きさで表示される
- PageSpeed（モバイル）で性能スコアの目安を満たす（LCP 2.5秒以内）
- プレビューURLでユーザーが確認し、OKを出せる状態になっている
